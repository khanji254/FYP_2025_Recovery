\section{Methodology}\label{sec:methodology}

This chapter outlines the approach taken to improve upon the existing coffee berry
sorting machine. The work spans three areas: a performance audit of the original
system, targeted improvements to the sorting mechanism, and evaluation of upgraded
processing hardware with a retrained classification model.

\subsection{Performance Analysis of Existing Machine}
\label{subsec:sysanalysis}

A structured performance audit of the existing sorting machine was conducted to quantify the root causes of its three documented limitations: motion blur, processing latency, and classification accuracy. The audit included:

\begin{itemize}
  \item Measuring end-to-end pipeline latency (frame capture $\rightarrow$ inference $\rightarrow$ actuation trigger) under realistic operating conditions.
  \item Evaluating classification accuracy on a held-out set of berry images collected directly from the machine at operating speed, where motion blur was most evident.
  \item Characterising the rolling-shutter distortion of the original Raspberry Pi Camera V2 at chute speeds of 0.4--0.6\,m\,s$^{-1}$.
  \item Identifying the contribution of the Raspberry Pi~4 running a serialised single-threaded pipeline to throughput bottlenecks.
\end{itemize}

These findings directly informed the improvements described in the following sections.

\subsection{Mechanical Subsystem — Retained and Fabricated}
\label{subsec:mechanical}

The mechanical subsystem of the coffee berry sorting machine was originally designed and fabricated by a previous team of fifth-year mechatronic engineering students at JKUAT \cite{mugo2017}. Their work established the structural framework, berry feeding mechanism, chute, and ejection arrangement that form the physical backbone of the sorting system. This project acknowledges and builds upon that foundational design work. Since the mechanical components are being re-fabricated for the improved system, the design specifications from the original project have been reviewed, retained, and re-used as the basis for fabrication.

\subsubsection{Berry Feeding Mechanism}

Berries are loaded into a hopper and fed onto the inspection chute via a \textbf{vibrating feeder trough}. An eccentric-mass DC vibrating motor, mounted beneath the trough, imparts periodic vibration that causes berries to advance along the trough in a singulated stream toward the imaging and ejection zone. The vibration frequency and amplitude are controlled by PWM from the ESP32, allowing feed rate to be adjusted. Figure~\ref{fig:mech_hopper} and Figure~\ref{fig:mech_feeder} show the hopper and feeder trough respectively.

\subsubsection{Inspection Chute and Ejection}

From the feeder trough, berries transit through the \textbf{inspection chute} where the camera captures frames for classification. Berries classified as \texttt{reject} are diverted by \textbf{pneumatic air ejector nozzles} mounted in the ejector holder; a short burst of compressed air deflects the berry into the reject bin. Berries classified as \texttt{accept} continue to the accept bin unimpeded. \subsection{Dataset Collection and Model Training}
\label{subsec:dataset}

The classification model was rebuilt from the ground up using upgraded hardware and a purpose-built binary dataset. The \textbf{Raspberry Pi~4 (4\,GB RAM)} was selected as the inference platform, providing a quad-core Cortex-A72 at 1.5\,GHz and approximately 3$\times$ the memory bandwidth of earlier Pi generations, allowing inference to run concurrently with frame capture. The MobileNetV2 TFLite classifier was replaced with \textbf{YOLOv11n}, retrained on a new binary dataset that consolidates the original four ambiguous ripeness classes into two well-separated outcomes.

\subsubsection{Image Acquisition}

A dataset of \textbf{2{,}000} annotated images was compiled, balanced across the
\texttt{accept} and \texttt{reject} classes. Images were sourced from:
\begin{enumerate}
  \item Static tabletop photographs taken under controlled LED lighting (multiple angles and distances).
  \item In-situ frames extracted from video captured on the actual chute at operational speed.
\end{enumerate}

Images were captured using the \textbf{Arducam OV9281 Global-Shutter Camera Module}
(Raspberry Pi CSI-2 interface, 1\,MP, 1280\,\texttimes{}800 native resolution, Sony OV9281 sensor).
The global-shutter sensor exposes all pixels simultaneously, eliminating the rolling-shutter
motion smear that degraded classification in the reference system (see Section~\ref{subsec:shutter}).
Images were saved at $1280 \times 800$ and subsequently centre-cropped and resized to
$640 \times 640$ for training.

\textit{Note: The mechanical chute and vibrating eccentric-motor feeder are retained unchanged
from the reference machine \cite{mugo2017}. Improvements in this project are confined to
the electronics, imaging, and software sub-systems.}

\subsubsection{Annotation}

All images were annotated with bounding boxes and class labels using the Roboflow annotation platform.
A \textbf{binary} classification scheme is adopted (see Section~\ref{subsec:binary}): berries are
labelled as either \texttt{accept} (commercially ripe, uniform deep-red) or \texttt{reject}
(all other states: unripe green, semi-ripe yellow/orange, overripe dark/black, physically damaged).
This aligns with Kenyan cooperative grading standards and eliminates the semi-ripe/ripe
boundary confusion that degraded the reference model.

The annotated dataset was split 70\% train / 15\% validation / 15\% test using the \texttt{split\_dataset.py} utility developed as part of this project.

\subsection{Sorting Mechanism Improvements}
\label{subsec:integration}

Based on the performance audit findings, three targeted upgrades were designed and implemented to address the root causes of poor sorting performance:

\begin{enumerate}
  \item \textbf{Camera replacement:} The rolling-shutter Raspberry Pi Camera V2 was
        replaced with the Arducam OV9281 global-shutter module to eliminate motion blur.
  \item \textbf{Ejector driver upgrade:} The PN2222A BJT transistors in the solenoid
        driver stages were replaced with IRLZ44N logic-level MOSFETs to improve
        switching speed and reliability at 3.3\,V ESP32 drive levels.
  \item \textbf{ESP32 co-processor:} An ESP32 microcontroller was introduced between
        the Raspberry Pi and the actuators to take over all hard real-time
        tasks --- solenoid timing, motor PWM, relay switching --- relieving the Pi's
        Linux scheduler from deterministic GPIO control.
\end{enumerate}

\subsubsection{Hardware Platform}

The system employs a co-processing architecture. The Raspberry Pi~4 (4\,GB RAM)
acts as the main inference engine handling image acquisition, YOLOv11 inference, and
object tracking. The ESP32 microcontroller handles time-critical real-time tasks:
solenoid trigger timing, motor PWM, and compressor control. Communication between
the two processors is over UART at 115\,200\,baud.

\subsubsection{Detection-to-Actuation Pipeline}

The pipeline operates as follows:
\begin{enumerate}
  \item Pi Camera captures a frame from the detection zone.
  \item YOLOv11 performs inference to detect and classify berries in the frame
        (Figure~\ref{fig:processing_flow}).
  \item Detected berry positions are tracked across frames using a centroid tracker
        \cite{bewley2016}.
  \item When a tracked berry reaches the ejection zone, the Pi sends a binary decision
        (\texttt{ACCEPT} or \texttt{REJECT:n} where $n$ is the ejector index) to the
        ESP32 via UART (Figure~\ref{fig:uart_flow}).
  \item ESP32 fires the corresponding solenoid jet for a calibrated pulse duration;
        \texttt{ACCEPT} commands generate no solenoid activation.
\end{enumerate}

Each ejector solenoid circuit includes a 220\,$\Omega$ gate resistor for current limiting and a 100\,k$\Omega$ pull-down to prevent false firing on power-up. A flyback diode (1N4007, cathode to +12\,V) across each solenoid suppresses inductive transient kickback when the MOSFET switch opens.

\subsubsection{Transistor Technology Selection: BJT vs.\ Logic-Level MOSFET}
\label{subsubsec:bjt_vs_mosfet}

The reference machine used bipolar junction transistors (BJTs --- PN2222A / BC547)
as the switching elements in the ejector solenoid driver stages. While BJTs are
cheap and widely available, they impose a fundamental switching-speed penalty that
becomes critical in a timer-sensitive ejection circuit.

\begin{table}[H]
  \centering
  \caption{BJT (PN2222A) vs.\ Logic-Level MOSFET (IRLZ44N) switching comparison}
  \label{tab:bjt_vs_mosfet}
  \small
  \begin{adjustbox}{max width=\linewidth}
  \begin{tabular}{@{}lll@{}}
    \toprule
    \textbf{Parameter} & \textbf{BJT (PN2222A)} & \textbf{MOSFET (IRLZ44N)} \\ \midrule
    Control mechanism & Current-controlled ($I_B$) & Voltage-controlled ($V_{GS}$) \\
    Drive voltage from ESP32 & Must source $\sim$5\,mA base current & Gate capacitance only; $<$1\,mA \\
    Turn-on threshold & $V_{BE} \approx 0.7$\,V (forward bias) & $V_{GS(th)} = 1$--$2$\,V (logic-level gate) \\
    Storage time (turn-off delay) & $t_{stg} = 200$--$600$\,ns & None (no minority carrier storage) \\
    Turn-on time $t_r$ & $\approx 100$\,ns & $< 20$\,ns (gate charge limited) \\
    Turn-off time $t_f$ & $\approx 250$\,ns + storage time & $< 50$\,ns \\
    On-state voltage drop & $V_{CE(sat)} \approx 0.3$\,V & $V_{DS(on)} = I_D \times R_{DS(on)} \approx 50$\,mV at 1\,A \\
    Maximum current (continuous) & 600\,mA & 47\,A \\
    Suitability at 3.3\,V gate/base & Marginal ($V_{BE}$ barely saturates) & Full enhancement; specified at 3.3\,V \\
    \bottomrule
  \end{tabular}
  \end{adjustbox}
\end{table}

The critical advantage of the MOSFET for this application is the absence of
\textbf{minority carrier storage time}. A BJT in saturation accumulates charge
carriers in the base region; when the switching signal is removed these must
recombine before the transistor turns off, adding 200--600\,ns of
unavoidable delay. For a solenoid fired within a 45\,ms timing window at a
chute speed of 0.5\,m\,s$^{-1}$, this is negligible in isolation, but when
combined with upstream inference latency any additional margin matters.

The MOSFET also operates with negligible gate drive current from the ESP32
3.3\,V rail, whereas the BJT requires the GPIO to source $\approx$5\,mA of
base current. With four simultaneous ejectors the BJT design loads the
microcontroller's output stage; the MOSFET design imposes essentially zero
steady-state GPIO load.

For these reasons the IRLZ44N logic-level MOSFET replaces the PN2222A BJT
across all four ejector channels, the motor driver, and the LED strip driver.

\subsubsection{Solenoid Driver Circuit}

Each of the four ejector channels uses an identical N-channel MOSFET stage. The
ESP32 GPIO output (3.3\,V logic) drives the IRLZ44N gate through a 220\,$\Omega$
series resistor, which limits gate-charge current and damps any parasitic resonance
with the gate capacitance. A 100\,k$\Omega$ pull-down resistor between gate and source
holds the MOSFET firmly off during ESP32 power-up and reset, preventing false
solenoid firing. The solenoid coil (12\,V, $\approx$22\,$\Omega$ DC resistance) is
connected between the drain and the 12\,V supply rail. A 1N5819 Schottky flyback
diode, cathode to +12\,V and anode to the drain, clamps the inductive back-EMF spike
to within the diode's forward voltage (0.3--0.5\,V) above the rail when the MOSFET
turns off. The source is tied directly to the common ground reference that connects
the 12\,V actuator supply and the ESP32 logic supply, ensuring no ground-loop offset
between the control and power sections. This circuit topology corresponds directly to
the design verified in Proteus and tabulated in Table~\ref{tab:wiring}.

\subsection{Circuit Simulation in Proteus}
\label{subsec:proteus}

Prior to physical breadboard construction, the ESP32-based control circuit was
designed and verified using \textbf{Proteus ISIS} (Labcenter Electronics).
Proteus supports simulation of the ESP32 microcontroller alongside IRLZ44N MOSFET
drivers, relay circuits, solenoid load models, and UART virtual terminals, enabling
full functional verification before any hardware was procured.
Figure~\ref{fig:proteus_full} in Chapter~4 shows the complete Proteus schematic.

\subsubsection{Simulation Scope}

The simulation covered the following subsystems:
\begin{itemize}
  \item \textbf{UART communication:} Simulated serial exchange between a virtual UART terminal (representing the Raspberry Pi) and the ESP32. Correct baud rate, 8N1 frame format at 115\,200\,bps, and message parsing logic were verified using Virtual Serial Port instruments.
  \item \textbf{Solenoid ejector drivers:} Four N-channel MOSFET switching stages (one per ejector), each with 220\,$\Omega$ gate resistor, 1N4007 flyback diode, and 100\,k$\Omega$ pull-down, were simulated and switching waveforms verified against the specification in Table~\ref{tab:wiring}.
  \item \textbf{Vibrating motor PWM control:} GPIO~14 PWM output was simulated into a motor load model; variable duty cycle confirmed correct speed control behaviour.
  \item \textbf{Relay-based compressor control:} GPIO~21 relay circuit verified for correct ON/OFF sequencing and protection diode operation under simulated load.
  \item \textbf{LED status indicator:} GPIO~22 PWM dimming into an LED model confirmed brightness control from 0\% to 100\%.
\end{itemize}

\subsubsection{Simulation Methodology}

The ESP32 firmware was compiled (Arduino framework) and loaded into the Proteus virtual ESP32-WROOM-32 component. Input stimuli consisting of binary classification command strings (e.g., \texttt{REJECT:1}, \texttt{REJECT:3}, \texttt{ACCEPT}) were injected via a virtual serial terminal scripted to replicate Raspberry Pi UART output. Oscilloscope probes were placed on each MOSFET gate pin and solenoid node to capture switching waveforms. The simulation confirmed correct actuation of all four ejector channels, motor PWM
behaviour, compressor relay switching, and UART framing before physical construction
commenced. The complete Proteus schematic and waveform captures from this simulation
are presented as results in Section~\ref{subsec:obj2results}.

\subsection{Validation Strategy}

System performance will be validated through:
\begin{itemize}
  \item \textbf{image test:} Run the YOLOv11 model on the held-out test set and report mAP@0.5, mAP@0.5:0.95, per-class precision and recall.
  \item \textbf{Throughput test:} Measure berries processed per minute at several belt speeds and identify the optimal operating point.
  \item \textbf{Latency test:} Measure end-to-end pipeline time from frame capture through YOLOv11 inference to UART solenoid trigger on the Pi~4 + ESP32 hardware.
\end{itemize}

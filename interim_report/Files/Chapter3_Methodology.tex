\section{Methodology}
\label{sec:methodology}

This chapter presents the \textit{what, why, and how} of the N4 recovery-system design
process in line with the final-report guidelines, containing design considerations,
calculations, circuit and CAD development workflow, and implementation planning
for each subsystem.

\subsection{Design Approach and Subsystem Decomposition}
The development of the N-4 recovery system relies on rigorous decomposition of
the mechatronic payload into isolated functional domains, isolating mechanical
load paths, high-current ignition routing, and low-voltage computational
electronics into independent modules.

\subsection{Methodology Structure}

The N-4 recovery work follows an iterative design--build--test cycle structured
into two orthogonal views: (A)~project phases and (B)~implementation modules.

\paragraph{Project phases}
\begin{enumerate}[leftmargin=*]
  \item Requirements definition --- derive subsystem requirements from mission
    constraints and safety limits.
  \item Concept generation --- produce candidate mechanical, electrical, and
    software solutions.
  \item Concept selection --- evaluate candidates against performance,
    manufacturability, and safety.
  \item Design and build --- produce CAD, schematics, and prototype hardware.
  \item Firmware implementation --- develop modular ESP32 firmware and
    inter-module interfaces.
  \item Validation and testing --- staged bench and system-level tests, logging,
    and pre-flight checks.
\end{enumerate}

\paragraph{Implementation modules} (concurrent workstreams):
\begin{enumerate}[leftmargin=*]
  \item Telemetry and antenna strategy (XBee, beacon, ground-station).
  \item Pyrotechnic deployment and ignition control (PWM, MOSFET drive).
  \item Power and feedback instrumentation (ADS1115 monitoring, continuity
    sensing).
  \item Mechanical containment and avionics support structure (holder, battery
    pack).
  \item Embedded software and communication control (FSM, CommunicationManager).
\end{enumerate}

\subsection{Telemetry Module Design Methodology}

\subsubsection{Telemetry Module Scope}

The telemetry module covers flight-to-ground data transmission hardware, antenna
strategy, communication reliability constraints, and integration interfaces to the
ESP32 flight computer firmware \cite{xbee_manual,n4_comm_architecture,n4_xbee_integration}.

\subsubsection{Telemetry Design Considerations}

\begin{itemize}
  \item Minimum operational range of at least 5\,km line-of-sight.
  \item Robust packet delivery with low drop rate in dynamic flight attitude.
  \item Simple and deterministic integration with ESP32 UART telemetry output.
  \item Field-deployable ground-station setup without complex infrastructure.
  \item Compatibility with future communication redundancy (beacon/MQTT fallback).
\end{itemize}

\subsubsection{Communication Mode Architecture and the Beacon Protocol}

The N-4 flight computer implements three independent communication channels
managed by a software \texttt{CommunicationManager} \cite{n4_comm_architecture}:
(1)~MQTT over WiFi for close-range pad operations, (2)~the 900\,MHz XBee link
for primary long-range recovery telemetry, and (3)~a beacon protocol as a
redundant fallback channel.

The beacon system injects raw 802.11 management frames carrying the telemetry
CSV payload in a vendor-specific information element. A ground-station ESP32
running in promiscuous mode captures all frames that match the payload magic
number. The return path uses ESP-NOW unicast packets. The beacon system has
been field-tested to 4\,km line-of-sight using a 2.4\,GHz duck antenna and
inline signal amplifier on the rocket side \cite{n4_beacon_configuration}.

\subsubsection{Antenna Options and Selection Using Link-Budget Math}

Table~\ref{tab:antenna_compare_method} summarises candidate antennas. The baseline
antenna pair is the 900\,MHz duck dipole. Free-space path loss (FSPL) is
modelled as \cite{xbee_manual,arrl_antenna_book}:

\begin{equation}
  \mathrm{FSPL}\,(\mathrm{dB}) = 20\log_{10}(d) + 20\log_{10}(f) - 147.55
  \label{eq:fspl}
\end{equation}

where $d$ is the link distance in metres and $f$ is the carrier frequency in
hertz. At the N-4 target range of $d = 5{,}000$\,m and $f = 915 \times 10^6$\,Hz,
$\mathrm{FSPL} = 105.66$\,dB. Received power is:

\begin{equation}
  P_\mathrm{rx} = P_\mathrm{tx} + G_\mathrm{tx} + G_\mathrm{rx} - \mathrm{FSPL}
  \label{eq:link_budget}
\end{equation}

With $P_\mathrm{tx} = +24$\,dBm and $G_\mathrm{tx} = G_\mathrm{rx} = 2$\,dBi,
$P_\mathrm{rx} = -77.66$\,dBm. Link margin:

\begin{equation}
  \mathrm{Margin} = P_\mathrm{rx} - P_\mathrm{sens} = -77.66 - (-110) = \mathbf{32.34\,dB}
  \label{eq:link_margin}
\end{equation}

This leaves significant headroom for atmospheric loss, multipath fading, and
small misalignments.

\subsection{Electrical Module with Deployment Submodule Methodology}

\subsubsection{Electrical + Deployment Module Scope}

This module covers onboard signal interfacing, telemetry electrical routing,
power/continuity monitoring, and pyrotechnic actuation electronics.

\subsubsection{Design Considerations}

\begin{itemize}
  \item Limited available pins on ESP32 requiring protocol-level optimisation
    between UART and I$^2$C paths.
  \item XBee requires hardware serial with remapped RX/TX pins.
  \item ADC expansion over I$^2$C for monitoring beyond native MCU pin allocation.
  \item Electronics stack must fit inside the 95\,mm avionics bay.
  \item Deployment channel validated against 16.8\,V fully charged 4S LiPo input
    and 14\,V minimum arm threshold.
  \item Pyro switching must be compatible with 3.3\,V logic drive.
\end{itemize}

\subsubsection{Power-Monitoring Calculations (ADS1115)}
\label{sec:ads1115_calc}

The monitoring path uses a 4.7\,k$\Omega$/1.1\,k$\Omega$ voltage divider into
the ADS1115 \cite{ads1115_datasheet}. The divider output:

\begin{equation}
  V_\mathrm{ADC} = V_\mathrm{in} \cdot \frac{R_2}{R_1 + R_2} = V_\mathrm{in} \cdot \frac{1.1}{4.7 + 1.1}
  \label{eq:vadc_divider}
\end{equation}

For $V_\mathrm{in} = 16.8$\,V: $V_\mathrm{ADC} \approx 3.186$\,V.
For $V_\mathrm{in} = 14.0$\,V: $V_\mathrm{ADC} \approx 2.655$\,V.

The ADS1115 is configured at $\pm$4.096\,V FSR (16-bit). Digital codes:

\begin{align}
  N_{16.8} &\approx 25{,}487 \quad (V_\mathrm{in} = 16.8\,\mathrm{V})\\
  N_{14}   &\approx 21{,}242 \quad (V_\mathrm{in} = 14.0\,\mathrm{V})
  \label{eq:adc_codes}
\end{align}

These ranges provide clear monitoring margin below ADC full-scale while
preserving sensitivity to deployment-state transitions.

\subsubsection{Deployment PWM and MOSFET Selection}
\label{sec:pwm_calc}

\noindent\textbf{(a) Nichrome wire element characterisation.}
The igniter elements use 26\,AWG nichrome wire with linear resistance
$\rho_\mathrm{NiCr} \approx 8.5\,\Omega/\mathrm{m}$ \cite{nichrome_ignition}.
For a 10\,cm bridge-wire element:

\begin{equation}
  R_\mathrm{elem} = \rho_\mathrm{NiCr} \cdot l_e = 8.5 \times 0.10 = 0.85\,\Omega
\end{equation}

At $V_\mathrm{target} = 6.0$\,V:

\begin{equation}
  I_\mathrm{elem} = \frac{V_\mathrm{target}}{R_\mathrm{elem}} = \frac{6.0}{0.85} \approx 7.06\,\mathrm{A}
  \qquad
  P_\mathrm{wire} = \frac{V_\mathrm{target}^2}{R_\mathrm{elem}} = \frac{36}{0.85} \approx 42.4\,\mathrm{W}
\end{equation}

\noindent\textbf{(b) PWM duty-cycle model.}
Average output voltage proportional to duty cycle \cite{pwm_heating,barr_pwm}:

\begin{equation}
  D = \frac{V_\mathrm{target}}{V_\mathrm{supply}} = \frac{6.0}{15.0} = 0.40
  \quad (40\%\;\mathrm{duty\;cycle})
\end{equation}

Field-validated deployment uses 70\% PWM duty cycle for reliable ignition with
nichrome integrity preserved across repeated firings.

\noindent\textbf{(c) IRLZ44N MOSFET selection.}
Conduction loss \cite{irlz44n_datasheet}:

\begin{equation}
  P_\mathrm{cond} = I^2 \cdot R_\mathrm{DS(on)}
\end{equation}

For $I = 3$\,A with IRLZ44N ($R_\mathrm{DS(on)} = 22$\,m$\Omega$):
$P_\mathrm{cond} \approx 0.20$\,W, compared to $\geq 0.45$\,W for a
non-logic-level IRF-series part at the same gate drive. The lower dissipation
and reliable 3.3\,V gate compatibility motivate selecting IRLZ44N.

\subsection{Structural (Mechanical) Module Design Methodology}

\subsubsection{Structural Module Scope}

The structural module defines the flight-computer holder, battery-carrier
geometry, threaded-rod integration, mounting-hole allocation, and interface
provision for the XBee extension board and BMS.

\subsubsection{Structural Design Considerations}

\begin{itemize}
  \item Fit within the 95\,mm avionics-bay envelope.
  \item Survive launch and deployment shock/vibration events (design baseline:
    up to 4\,$g$ sustained, with higher pop-test transients).
  \item Package four 18650 cells in parallel while avoiding rod interference.
  \item Maintain two threaded rods at 50\,mm spacing and approximately 6\,mm
    offset from the rear holder reference edge.
  \item Raise edge battery seats relative to mid seats so outer cells clear rod
    paths.
  \item Provide mounting provision above battery holders for XBee extension and
    BMS.
\end{itemize}

\subsubsection{Structural Load Calculations}

\paragraph{(a) Battery pack mass and weight.}
For $n_\mathrm{cells} = 4$ cells at $m_\mathrm{cell} \approx 0.047$\,kg
each \cite{panasonic_cgr18650da_datasheet}:

\begin{equation}
  m_\mathrm{pack} = 4 \times 0.047 = 0.188\,\mathrm{kg}
  \qquad
  W_\mathrm{pack} = 0.188 \times 9.81 \approx 1.84\,\mathrm{N}
\end{equation}

\paragraph{(b) Launch inertial force (4\,$g$ design case).}

\begin{equation}
  F_\mathrm{launch} = m_\mathrm{pack} \times 4g = 0.188 \times 39.24 \approx 7.38\,\mathrm{N}
\end{equation}

\paragraph{(c) Pop-test pressure-driven force (188\,kPa reference).}

\begin{equation}
  A_{95} = \pi\left(\frac{0.095}{2}\right)^2 \approx 7.09 \times 10^{-3}\,\mathrm{m}^2
  \qquad
  F_\mathrm{pop} = 188{,}000 \times 7.09 \times 10^{-3} \approx 1{,}330\,\mathrm{N}
\end{equation}

\paragraph{(d) Load distribution through fasteners.}
Under $F_\mathrm{pop} \approx 1{,}330$\,N: 4 points carry $\sim$332\,N each; 8
points carry $\sim$166\,N each. This motivates the distributed screw fastening
strategy.

\subsubsection{Communication Manager Architecture}

All three channels are coordinated by the \texttt{CommunicationManager} class,
which selects and combines active transmission modes at runtime. Mode-selection
logic supports automatic fallback from MQTT to beacon when WiFi is lost, and
allows runtime switching between all three modes via serial, MQTT, or ESP-NOW
commands \cite{n4_comm_architecture}.

\subsubsection{Firmware State Machine Architecture}

The firmware is structured as a finite-state machine (FSM) executed inside the
ESP32 \texttt{main loop()}, with telemetry transmission running continuously
across all states via hardware serial interrupt. States:
\texttt{PAD} $\to$ \texttt{ARMED} $\to$ \texttt{BOOST} $\to$ \texttt{APOGEE}
$\to$ \texttt{DROGUE} $\to$ \texttt{MAIN} $\to$ \texttt{LANDED}.

\subsubsection{Pyrotechnic Deployment Software Flow}

The deployment channel is driven only when the FSM reaches the APOGEE or
RECOVERY state and all pre-fire checks pass \cite{n4_pyro_control,n4_pwm_config}.

Key firmware constants:
\begin{itemize}
  \item \texttt{PWM\_DUTY\_IGNITE = 178} ($D = 0.70$, 70\% duty cycle)
  \item \texttt{LAUNCH\_INHIBIT\_V = 14.0\,V} --- minimum battery voltage for
    arm enable
  \item \texttt{CHUTE\_COUNT\_THRESHOLD = 1000} --- ADS1115 ADC counts for
    continuity present
  \item \texttt{PWM\_FREQ = 1000\,Hz} --- LEDC timer frequency for ignition
    channel
\end{itemize}

\subsubsection{Power Monitoring Software Integration}

Battery voltage and chute-channel continuity are read from the ADS1115 over
I$^2$C and back-calculated using the inverse of the hardware voltage
divider \cite{ads1115_datasheet,voltage_divider_theory}:

\begin{equation}
  V_\mathrm{battery} = V_\mathrm{ADC} \times \frac{R_1 + R_2}{R_2} = V_\mathrm{ADC} \times \frac{57.0}{10.0}
  \label{eq:vbat_reconstruct}
\end{equation}

If the reconstructed value falls below \texttt{LAUNCH\_INHIBIT\_V}, the deployment
arm flag is cleared and a ``\texttt{PWR INHIBIT}'' status byte is broadcast over
XBee to the ground station before launch.

\subsection{Validation and Test Method}

Testing is staged from component to full-system level:
\begin{enumerate}
  \item \textbf{Component level:} PWM-output verification, continuity checks,
    and ADC calibration.
  \item \textbf{Subsystem level:} Telemetry range trials, ignition repeatability
    tests, and enclosure leak/charring checks.
  \item \textbf{System level:} Integrated ground rehearsal with full communication
    stack and deployment command-path validation.
  \item \textbf{Field level:} Open-terrain XBee range test, dual deployment pop
    test, and drone-mounted simulated flight.
\end{enumerate}
